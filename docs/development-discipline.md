# 开发纪律与提交规范

日期：2026-06-12

## 1. 总原则

本项目的评分不仅看最终效果，也看开发过程。开发过程必须能证明作品是持续完成、独立完成、结构清晰、可复现、可解释的。

所有开发活动遵守以下原则：

- 小步提交。
- 每个 PR 只做一件事。
- 主分支始终可运行。
- PR 描述必须真实、完整、可验证。
- 依赖、模型、参考代码必须公开说明。
- 不提交密钥、隐私数据、模型权重和构建产物。

## 2. 分支策略

推荐分支：

- `main`：稳定主分支，合并后应可运行。
- `docs/*`：文档类改动。
- `feat/*`：功能类改动。
- `test/*`：测试类改动。
- `fix/*`：缺陷修复。

每个功能从独立分支发起 PR，合并后删除分支。

## 3. PR 规范

每个 PR 只实现或修改单一功能。大功能必须拆分。

PR 必须包含：

- 标题：一句话说明新增或修改了什么。
- 功能描述：说明功能作用和使用方式。
- 实现思路：说明技术选型或核心逻辑。
- 测试方式：说明如何验证功能正常。
- 影响范围：说明影响哪些模块或文档。
- 依赖说明：如新增依赖，说明用途和原创边界。

禁止：

- 空白 PR 描述。
- PR 描述与实际代码严重不符。
- 一个 PR 混合多个无关功能。
- 最后一天一次性导入所有代码。

## 4. Commit 规范

Commit 应当粒度清晰，能反映真实开发过程。

推荐格式：

```text
docs: define project discipline
feat: add drawing state model
feat: add browser speech provider
test: cover command parser cases
fix: handle unavailable speech recognition
```

要求：

- 每个 commit 时间戳必须落在实训营允许开发周期内。
- 不伪造他人提交。
- 不把旧项目整体搬入本仓库。
- 复用自己过去的代码片段时，在 PR 描述中注明来源和改动。

## 5. Definition of Done

一个 PR 合并前至少满足：

- 功能或文档目标明确完成。
- 本地验证通过。
- README 或设计文档按需更新。
- 无密钥、隐私数据、无关文件和构建产物。
- 新增依赖已说明。
- 主分支合并后仍可运行。

核心功能 PR 还应满足：

- 有单元测试或清晰手动测试记录。
- 错误场景有处理。
- 用户可从界面获得反馈。
- 影响 Demo 的行为已记录。

## 6. 测试纪律

测试记录分为自动测试和手动测试。

自动测试优先覆盖：

- 指令文本到绘图操作的解析。
- 复杂指令拆解。
- 画布状态更新。
- 撤销和重做。
- 错误输入和模糊指令。

手动测试必须记录：

- 浏览器名称和版本。
- 操作系统。
- 麦克风输入方式。
- 测试语音指令。
- 实际结果。

## 7. 文档纪律

以下内容发生变化时必须更新文档：

- 支持的新语音指令。
- 新增第三方依赖。
- 新增模型或外部服务。
- Demo 启动方式。
- 已完成或放弃的用户故事。
- 已知问题和规避方式。

最终提交前，README 必须包含：

- 项目简介。
- 启动方式。
- 功能列表。
- 依赖声明。
- Demo 视频链接。
- 设计文档链接。
- 原创功能说明。

## 8. Demo 纪律

Demo 视频需要用声音完整讲解并展示：

- 麦克风授权和语音输入。
- 基础图形绘制。
- 样式调整。
- 对象编辑。
- 撤销和重做。
- 复杂指令拆解。
- 容错或澄清。

Demo 脚本应在开发后期固定，避免临场随意发挥导致失败。

## 9. 安全与隐私

禁止提交：

- `.env`
- API key
- 私人录音
- 浏览器本地缓存
- 未压缩模型权重
- 包含个人隐私的测试数据

如需要模型 API key，必须使用环境变量或本地配置文件，并在 `.gitignore` 中排除。

## 10. 本项目特殊约束

- 正式产品交互必须以语音为主。
- 文本输入框只允许作为开发调试入口，不能作为 Demo 主路径。
- 浏览器语音识别是 MVP 主链路。
- 本地语音识别只保留接口和未来计划，不作为 MVP 完成标准。
- 所有绘图操作必须通过统一操作结构执行，避免各模块直接改画布状态。
