# VoxCanvas 项目开发文档

日期：2026-06-12

## 1. 项目背景

企业实训营给出两个选题，本项目选择题目二：AI 语音绘图工具。

题目要求用户不能使用鼠标或键盘，仅通过语音指令完成绘图创作。评审重点包括作品完整度与创新性、开发过程与质量、演示与表达。因此，本项目不把重点放在堆叠模型能力，而是做一个稳定的语音到绘图闭环，并通过清晰架构、持续 PR、可验证测试和完整 Demo 展示工程能力。

## 2. 产品目标

项目名称：VoxCanvas。

一句话定位：一个面向无障碍创作和快速草图表达的纯语音 AI 绘图工具。

核心体验：

1. 用户说出绘图意图。
2. 系统识别语音并转成文本。
3. 指令理解层将文本解析为一个或多个绘图操作。
4. 绘图引擎更新画布。
5. 系统用视觉状态和语音反馈告知执行结果。

## 3. MVP 范围

MVP 必须完成：

- 浏览器中打开应用并申请麦克风权限。
- 使用浏览器语音识别获得用户语音文本。
- 支持基础绘图指令：画圆、画矩形、画线条、画箭头、添加文字。
- 支持基础样式指令：颜色、大小、位置。
- 支持对象编辑：选择最近对象、移动、删除。
- 支持历史操作：撤销、重做、清空画布。
- 支持语音识别误差和口语化表达的语义容错，例如把“画一个园”理解为“画一个圆”，把“回到最初状态”理解为清空或恢复类意图。
- 支持复杂组合指令拆解，例如“画一座房子，有红色屋顶、黄色墙体、两个窗户和一扇门”。
- 支持无法理解时的澄清或失败提示。
- README、设计文档、Demo 说明与依赖声明完整。

MVP 暂不强制完成：

- 本地部署语音识别。
- 多人协作绘图。
- 图片生成模型。AI 生图可作为后期高级能力加入，用于处理“画一只蓝色的鸟”“换成水彩风格”等复杂视觉任务。
- 手绘笔刷级自由绘画。
- 生产级账户系统。

### 当前实现状态（PR-01）

PR-01 已建立可运行前端应用骨架，采用两边窄、中间宽的 Voice Workbench 布局。当前只包含静态语音状态、画布空状态、指令解释和反馈日志占位，不实现真实语音识别、绘图引擎、指令解析、操作队列、撤销重做或 AI/LLM 能力。

### 当前实现状态（PR-02）

PR-02 已建立画布状态模型、图形模型和统一绘图操作 schema。当前支持用纯函数将 `create_shape`、`update_shape`、`move_shape`、`delete_shape` 和 `clear_canvas` 操作应用到 `CanvasState`，并用单元测试覆盖状态变更、不可变更新和缺失目标操作。

PR-02 仍不渲染真实图形，不接入语音识别，不实现操作队列、撤销重做、对象引用解析或 AI/LLM 规划。它是后续 Canvas/SVG 渲染、指令解析和操作队列的状态基础。

### 当前实现状态（PR-03）

PR-03 已建立 SVG 画布渲染器，将 `CanvasState` 中的圆、矩形、线条、箭头和文本渲染为可见图形，并支持基础样式、坐标、尺寸、箭头 marker 和选中态可视反馈。该阶段曾使用静态 `demoCanvasState` 展示渲染结果，后续 PR-06 已切换为真实操作队列驱动的画布状态。

PR-03 仍不接入真实语音识别，不解析自然语言指令，不实现操作队列、撤销重做、对象引用解析或 AI/LLM 规划。它只完成从画布状态到可视画布的渲染层。

### 当前实现状态（PR-04）

PR-04 已建立 `SpeechProvider` 抽象和 `BrowserSpeechProvider` 浏览器实现，支持通过浏览器 `SpeechRecognition` / `webkitSpeechRecognition` 启动、停止语音识别，接收 interim/final transcript，归一化识别结果和错误状态。应用左侧语音面板已经接入开始/停止按钮、麦克风状态、错误提示和实时 transcript 展示。

PR-04 仍不解析自然语言指令，不执行绘图操作，不实现操作队列、撤销重做、对象引用解析或 AI/LLM 规划。它只完成语音输入到文本状态的入口，后续 PR-05 会把 transcript 接入基础指令解析。

### 当前实现状态（PR-05）

PR-05 已建立基础本地 `CommandParser`，支持将简单中文绘图文本解析为统一的 `DrawingOperation[]` 预览。当前覆盖圆形、矩形、线条、箭头、文字创建，支持基础颜色词、部分九宫格位置词和清空画布指令。应用右侧 Command trace 已接入真实解析结果，能够显示 parsed intent、operation preview 和解析反馈。

PR-05 仍不执行绘图操作，不更新真实 `CanvasState`，不实现操作队列、撤销重做、对象引用解析或 AI/LLM 规划。包含“它”“刚才”等对象引用的指令会返回暂不支持反馈，避免误判为新建图形。后续 PR-06 会把解析结果接入操作队列，形成 transcript 到画布变化的闭环。

### 当前实现状态（PR-06）

PR-06 已建立 `OperationQueue`，支持按批次顺序执行 `DrawingOperation[]`，并记录已执行批次，避免同一批操作在界面重渲染时重复落盘。应用画布从静态 demo 状态切换为真实 `CanvasState`，能够通过浏览器语音 transcript 或开发模拟 transcript 将基础创建指令和清空指令执行到 SVG 画布。

PR-06 仍不实现撤销、重做、对象引用解析、复杂指令规划或 AI/LLM 规划。后续历史管理和对象引用 PR 会继续完善多轮编辑语义。

### 当前实现状态（PR-07）

PR-07 已建立 `HistoryManager`，用 `past/present/future` 维护画布历史快照。应用画布现在读取 `history.present`，基础绘图和清空操作会提交新的历史状态，撤销和重做会在历史栈之间切换画布状态。顶部 Undo、Redo、Clear 按钮已从占位变为按历史状态启用；基础指令解析器也支持“撤销”“重做”，可通过浏览器语音 transcript 或开发模拟 transcript 触发同一历史管理逻辑。

PR-07 仍不实现对象引用解析、移动/删除类自然语言编辑、复杂指令规划或 AI/LLM 规划。当前撤销、重做恢复的是完整 `CanvasState` 快照；后续对象引用和复杂规划接入后，会继续复用同一历史层。

### 当前实现状态（PR-08）

PR-08 已建立基础对象引用解析能力。`CommandParser` 可以基于当前 `CanvasState` 将“它”“这个”“那个”解析为当前选中或最近对象，也可以将“刚才的圆”“刚才的矩形”等按类型引用解析为最近匹配对象。当前支持对象移动、删除、变色，以及“变大”“变小”这类基础尺寸调整；所有结果仍落到统一 `DrawingOperation`，由 `OperationQueue` 执行并进入 `HistoryManager`。

PR-08 仍不实现复杂对象消歧、多对象批量编辑、语义尺寸词细分或 AI/LLM 规划。若当前画布中没有可引用对象，系统会给出失败反馈而不是误创建新图形。

### 当前实现状态（PR-09）

PR-09 已建立语义规划基础层，但不接入真实 LLM。`SemanticCommandPlanner` 目前以规则解析结果为快速路径，并提供 mock semantic fallback，用统一 `SemanticPlanResult` 表达 `matched`、`unsupported` 和 `needs_clarification`。当缺少可引用对象时，应用可以在 Command trace 中展示澄清状态，而不是把模糊指令静默丢弃。

PR-09 同时建立 `OperationValidator`，对语义规划输出的结构化绘图操作做运行时校验。非法操作类型、缺失目标对象、非法图形参数等结果会被拦截，不会进入 `OperationQueue` 或修改 `CanvasState`。PR-09 仍不实现真实 LLM 语义容错、复杂组合拆解、AI 生图或语音改图；这些能力会在后续 PR 基于当前 schema 和 validator 接入。

### 当前实现状态（PR-10）

PR-10 接入 LLM Semantic Planner 的工程通道。应用仍以本地规则解析作为快速路径；当规则解析无法安全执行并返回 unsupported 时，前端只请求同源 `/api/semantic-plan`，由 Vite 本地代理在服务端读取 `OPENAI_API_KEY` 并调用 OpenAI Responses API。API key 不进入前端代码、测试 fixture 或仓库。

PR-10 使用结构化 JSON schema 要求模型输出 `SemanticPlanResult`，再通过既有 `OperationValidator` 校验 `DrawingOperation[]`。这使“画一个园”这类同音错字可以归一为创建圆形，“回到最初状态”这类自然表达可以归一为清空画布；如果 LLM 服务不可用，系统返回安全失败状态，不修改画布。

PR-10 仍不扩展新的绘图原语，不实现房子/流程图模板，不接入 AI 生图或语音改图。后续 PR-11/PR-12 会扩展结构化绘图能力，PR-13 之后再建立图片图层和生图/改图路线。

### 当前实现状态（PR-11）

PR-11 扩展了 `DrawingShapeKind`、`CommandParser`、`OperationValidator` 和 SVG 渲染器，新增三角形、菱形和椭圆三类结构化图形原语。三角形可用于房子草图的屋顶，菱形可用于流程图判断节点，椭圆可用于流程图开始/结束节点。

新增原语仍然沿用既有 `create_shape` 操作，不绕过 `DrawingOperation`、`OperationQueue`、`CanvasState` 或历史管理。LLM planner 的系统提示也同步列出新的 `shape.kind`，方便后续 PR-12 输出合法结构化计划。

PR-11 仍不实现“画一座房子”“画一个流程图”的模板展开，也不新增复合对象分组、连接线自动布局或 AI 生图。结构化复合对象会在 PR-12 基于这些原语继续实现。

### 当前实现状态（PR-12）

PR-12 已建立 `ShapeTemplateExpander`，支持将“画一座房子，有红色屋顶、黄色墙体、两个窗户和一扇门”和“画一个流程图”等结构化复合对象展开为多个合法 `create_shape` 操作。房子模板由墙体、屋顶、两个窗户和门组成；流程图模板由开始椭圆、箭头、判断菱形、处理矩形和文字标签组成。

模板展开仍然通过 `CommandParser`、`SemanticCommandPlanner`、`OperationValidator`、`OperationQueue`、`CanvasState` 和 `HistoryManager` 执行，不绕过现有状态模型。PR-12 同步扩展 `create_template` intent，用于表达模板规划意图；实际落地操作仍是可校验、可撤销、可继续编辑的原子图形。

PR-12 仍不实现复合对象分组、自动布局编辑、AI 生图、图片图层或语音改图。更复杂的视觉对象会在 PR-13 之后通过受管理图片图层和 AI 生图路线继续实现。

### PR-08 后的真实语音测试结论

PR-08 完成后，本地测试暴露出规则解析的主要边界：浏览器语音识别可能把“圆”转成“园”，用户也可能用“回到最初状态”“重新来”“全部清掉”等未写入规则表的自然表达。当前 `CommandParser` 依赖有限关键词和正则，适合低延迟、确定性的基础指令，但不能承担完整用户语义理解。

后续路线调整为三层能力路线：

1. 基础结构化绘图继续走 `DrawingOperation`、`OperationQueue` 和 SVG 画布，覆盖圆、矩形、箭头、文字、流程图和可编辑草图。
2. 加入 LLM Semantic Planner，解决语音识别误差、同音错字、口语化同义表达、任务路由和高风险模糊指令澄清。规则解析器继续作为快速路径；LLM 只负责理解语义和输出结构化计划，不直接修改画布。
3. 后期加入 AI 生图与语音改图路径，专门处理“画一只蓝色的鸟”“画一个水彩风格场景”等复杂视觉任务，并允许用户继续用“把蓝色换成红色”“换成水彩风格”等语音指令基于旧图生成新图。

原则是：LLM 负责理解语义和选择任务路线；规则、schema、validator 和图层模型负责约束边界。结构化绘图最终只能执行合法 `DrawingOperation`；AI 生图最终只能生成或替换受管理的图片图层，并进入历史记录以支持撤销。

### PR-01 前端骨架设计摘要

PR-01 的目标是先建立稳定、可运行、可验证的前端工作台，而不是提前实现语音识别或绘图业务逻辑。

桌面端采用三栏 Voice Workbench：

- 左侧窄栏：语音控制、麦克风状态、当前 transcript 和开发调试入口。
- 中间宽区：主画布工作区，优先保证画布面积和视觉焦点。
- 右侧窄栏：识别文本、解析意图、操作预览和反馈日志。

窄屏布局按任务优先级堆叠：顶部状态栏、画布、语音控制、指令解释与反馈日志。这样可以保证手机或窄屏下画布不会被侧栏挤到不可用。

技术上采用 Vite、React、TypeScript、Vitest 和 Testing Library。PR-01 暂不引入 UI 组件库，先用轻量组件和 CSS design tokens 固定信息架构、响应式布局、对比度、语义结构和可见 focus state。

可访问性目标以 WCAG 2.2 AA 作为设计与检查基线，但 MVP 阶段不声明正式认证。PR-01 至少保证页面结构语义清晰、基础控件可通过键盘访问、焦点可见、文字对比度可读。正式 Demo 仍以语音创作为主，文本模拟入口只作为开发调试能力。

## 6. 技术架构

整体采用前端优先架构。MVP 不引入复杂后端，除非复杂指令规划需要保护模型 API key。

核心模块：

- `SpeechProvider`：语音识别接口，输出标准化识别结果。
- `BrowserSpeechProvider`：浏览器语音识别实现，MVP 默认启用。
- `LocalSpeechProvider`：本地语音识别预留接口，MVP 不实现真实识别。
- `CommandParser`：解析简单、确定性强的绘图指令，作为低延迟快速路径。
- `SemanticCommandPlanner`：通过 OpenAI Responses API 处理语音识别误差、自然语言同义表达、复杂指令和澄清问题；前端只请求同源代理，API key 只保存在环境变量或后端配置中。
- `IntentRouter`：根据语义规划结果选择结构化绘图、AI 生图、图片编辑或澄清路线。
- `OperationValidator`：校验 LLM 或规则输出的操作，确保只能执行合法 `DrawingOperation`。
- `ShapeTemplateExpander`：将“房子”“流程图”等结构化复合对象展开为多个可编辑图形操作，或在 schema 扩展后生成更丰富的图形原语。
- `ImageGenerationService`：后期用于文生图和图生图编辑，生成或替换受管理的图片图层。
- `GeneratedImageLayer`：后期图片图层模型，保存图片 URL、原始 prompt、编辑历史、位置和尺寸，并接入历史管理。
- `OperationQueue`：按顺序执行绘图操作，支持复杂指令逐步落地。
- `DrawingEngine`：管理画布对象、渲染、选择、修改。
- `HistoryManager`：维护撤销、重做。
- `FeedbackService`：给出执行状态、错误提示和语音反馈。

数据流：

```text
麦克风输入
  -> SpeechProvider
  -> Transcript
  -> CommandParser
  -> SemanticCommandPlanner（规则无法覆盖或需要语义容错时）
  -> IntentRouter
     -> 结构化绘图：OperationValidator -> DrawingOperation[] -> OperationQueue -> CanvasState
     -> AI 生图：ImageGenerationService -> GeneratedImageLayer -> CanvasState
     -> 图片编辑：旧图 + 新指令 -> ImageGenerationService -> 替换 GeneratedImageLayer
     -> 澄清：FeedbackService
  -> FeedbackService
```

## 6.1 AI 生图后期路线

AI 生图用于处理结构化绘图不擅长的复杂视觉任务，例如“画一只蓝色的鸟”“画一个水彩风格的森林场景”。这类任务不强行拆成圆、矩形和线条，而是由语义规划层路由到图片生成路径。

模型路线与 PR-10 保持一致：语义理解优先使用 OpenAI Responses API；后续生图和语音改图优先使用 Responses API 的 `image_generation` 工具，以便在同一多轮上下文中保留旧图、图像 ID、上一轮 response 和新语音指令。若后续评测成本或效果要求变化，也可以把语义规划和图片生成拆成不同模型，但接口层保持 `SemanticCommandPlanner` 与 `ImageGenerationService` 分离。

第一版 AI 生图只考虑纯语音控制，不引入鼠标工具、橡皮、画笔或框选操作。用户可以继续通过语音修改生成图，例如“把鸟换成红色”“换一种扁平插画风格”“背景变成夜晚”。系统会把旧图、原始 prompt、编辑历史和新指令传给图片编辑模型，生成新图并替换当前图片图层；旧图仍进入历史记录，支持撤销。

AI 生图能力需要后端或安全代理保护 API key，也需要明确生成状态、失败反馈、图片缓存和依赖声明。若时间不足，该能力作为 PR-15 之后的后期扩展，不阻塞基础语音绘图 MVP。

## 6.2 LangGraph 引入判断

当前阶段暂不引入 LangGraph。VoxCanvas 仍以 React 前端、纯函数状态模型、规则解析、语义规划接口和少量服务调用为主；过早引入工作流框架会增加依赖、调试和部署复杂度。

后续出现以下需求时再重新评估 LangGraph：

- 语义规划、图片生成、图片编辑、重试、澄清和回放形成多节点长流程。
- 需要可视化调试 agent 工作流，或需要保存中间步骤供 Demo 解释。
- 需要跨多轮对话恢复任务状态，例如生成失败后继续修改、重试或切换模型。
- 需要同时编排多个模型或工具，并对分支、失败和人工确认做统一控制。

在这些需求出现前，优先用显式 TypeScript 接口、服务函数和测试覆盖实现工作流；等复杂度真正超过本地编排能力时，再把 LangGraph 作为独立架构 PR 评估。

## 7. 语音识别方案决策

MVP 采用浏览器语音识别作为主链路。

选择原因：

- 开发成本低，可以更快完成端到端闭环。
- 适合浏览器 Demo，评委无需额外安装本地语音服务。
- 延迟较低，便于展示语音到绘图的即时反馈。
- 把时间留给更能体现题目价值的指令理解、容错、复杂指令拆解和画布操作。

已知限制：

- `SpeechRecognition` 浏览器兼容性有限。
- 某些浏览器可能使用服务端语音识别，离线能力不可保证。
- 不同浏览器、语言环境、网络状态可能影响识别稳定性。

应对策略：

- README 明确推荐浏览器环境。
- 代码中检测 API 可用性并给出提示。
- 设计 `SpeechProvider` 抽象，避免业务逻辑绑定浏览器实现。
- 保留 `LocalSpeechProvider`，后续可接入 whisper.cpp、faster-whisper 或 Vosk。

## 8. 本地语音识别未来计划

本地语音识别不进入 MVP 强制范围，只作为未来增强。

未来可以选择：

- whisper.cpp：适合本地离线部署，支持量化和多平台推理。
- faster-whisper：适合 Python 服务端，推理性能较好。
- Vosk：轻量、离线、适合命令词场景。

预留接口目标：

```ts
interface SpeechProvider {
  start(): Promise<void>;
  stop(): Promise<void>;
  onResult(listener: (result: SpeechResult) => void): void;
  onError(listener: (error: SpeechError) => void): void;
}
```

MVP 阶段只实现浏览器版本，后续若时间允许，再实现本地服务版本。

## 9. 指令理解策略

为了平衡响应延迟和理解能力，采用分层策略：

1. 确定性指令优先走本地规则解析，例如“画一个红色圆形”“撤销”“清空画布”。
2. 规则解析失败、识别结果疑似同音错字、自然口语表达或复杂组合指令进入 LLM Semantic Planner；PR-10 通过同源 `/api/semantic-plan` 代理调用 OpenAI Responses API。
3. LLM 先判断任务路线：结构化绘图、AI 生图、图片编辑、澄清或不支持。
4. 结构化绘图路线只输出结构化计划、纠错后的 transcript、置信度、澄清问题或 `DrawingOperation[]`，不能直接操作 DOM、SVG 或画布状态。
5. 所有结构化操作必须经过 schema 校验和 `OperationValidator`，非法操作、缺失目标、越界参数或低置信度结果不执行。
6. AI 生图路线生成图片图层，不生成任意前端代码；图片编辑路线基于旧图和新指令生成新图，并保留历史以支持撤销。
7. 模糊指令不强行执行，优先给出澄清，例如当前没有选中对象时听到“把它放大”，或“回到刚才那个样子”无法确定是撤销还是清空时。
8. 结构化复合对象通过 schema 扩展、图形原语扩展或模板展开器转成多个合法 `DrawingOperation`；复杂视觉对象和风格化画面优先走 AI 生图路径。

## 10. 成本与延迟控制

虽然题目二没有像题目一明确要求端云成本控制，但成本和延迟会影响演示质量。

策略：

- 简单指令本地解析，不调用 LLM。
- 识别误差、自然语言归一、模糊澄清和复杂指令才进入 AI 规划层。
- 云端 LLM API key 必须保存在后端或本地环境变量中，不能进入前端代码或仓库。
- PR-10 默认模型通过 `VOXCANVAS_LLM_MODEL` 配置，当前文档建议值为 `gpt-5.4-mini`，实际可用模型名以本地环境变量和 OpenAI 控制台为准。
- 图片生成或图片编辑 API key 同样必须通过后端或安全代理保护，生成图片缓存和外部服务依赖必须在 README 与 PR 描述中说明。
- 对相同指令解析结果做轻量缓存。
- AI 生图和图片编辑属于高延迟路径，界面必须显示生成中、失败和可重试状态。
- Demo 脚本优先覆盖稳定指令，避免依赖不可控网络。
- 保留离线 STT 方向作为未来隐私和成本优化。

## 11. 测试策略

测试分三层：

- 单元测试：指令解析、操作生成、画布状态变更、撤销重做。
- 集成测试：输入语音文本，验证生成的绘图操作和画布对象。
- 手动验收：用真实麦克风完成 Demo 脚本，记录浏览器、设备、识别语言和测试结果。

每个 PR 必须说明测试方式。无法自动化验证的语音交互，需要提供手动测试步骤。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 浏览器语音识别不可用 | 无法语音输入 | 检测 API 并提示推荐浏览器，保留文本模拟入口仅用于开发测试 |
| 语音识别误差 | 指令执行错误 | 使用 LLM Semantic Planner 做上下文纠错、同音词修正、别名映射和确认机制 |
| 复杂指令不可控 | 画布结果混乱 | 统一操作 schema，先规划再执行 |
| LLM 输出不稳定 | 执行错误操作或生成不可控图形 | 使用结构化输出、schema 校验、OperationValidator、置信度阈值和澄清流程 |
| LLM API key 泄露 | 安全风险 | API key 只放环境变量或后端配置，不提交仓库，不写入前端代码 |
| LLM 延迟过高 | 影响语音绘图流畅度 | 明确规则快速路径，LLM 仅处理规则无法覆盖的语义任务 |
| 图片生成结果不可控 | 生成内容偏离用户意图 | 保留原始 prompt、编辑历史和失败反馈，允许用户语音重试或改写指令 |
| 图片生成服务不可用 | 复杂视觉任务失败 | 将 AI 生图作为后期增强，不阻塞结构化绘图主链路，并提供失败提示 |
| 图片生成成本过高 | Demo 不稳定或费用不可控 | 将图片生成限定为复杂视觉任务，简单图形继续走本地结构化绘图 |
| 过早引入 LangGraph | 增加依赖和调试复杂度 | 当前先用显式接口和服务函数；只有多节点长流程、重试恢复和工作流可视化成为刚需时再评估 |
| PR 记录不连续 | 作品可能无效 | 按迭代计划持续提交，小 PR 合并 |
| 最后一天突击提交 | 直接无效 | 从项目初期保留文档、脚手架、功能、测试、Demo 的连续记录 |
